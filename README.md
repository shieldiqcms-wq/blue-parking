# Blue Parking 🅿️

نظام إدارة موقف سيارات بواجهة عربية بالكامل (RTL)، مبني لمستخدم واحد (المالك)،
يعمل من الموبايل واللابتوب، ويُثبَّت على الجوال كتطبيق (PWA).

| | |
|---|---|
| **العملة** | الدينار الأردني (JOD) |
| **المنطقة الزمنية** | `Asia/Amman` — كل الحسابات بتوقيت الأردن |
| **المستخدمون** | حساب مالك واحد فقط، بلا تسجيل عام |
| **التقنيات** | React 18 · TypeScript · Vite · Tailwind CSS · Supabase (PostgreSQL + Auth + RLS) |
| **النشر** | GitHub Pages عبر GitHub Actions |
| **التكلفة** | الخطة المجانية في Supabase و GitHub — بلا أي API مدفوع |

## التشغيل السريع

```bash
# 1) تثبيت الحزم
npm install

# 2) إعداد متغيرات البيئة
cp .env.example .env.local
#    ثم عبّي القيمتين داخل .env.local

# 3) تشغيل خادم التطوير
npm run dev
```

ثم افتح `http://localhost:5173`.

### الأوامر المتاحة

| الأمر | الوظيفة |
|---|---|
| `npm run dev` | خادم التطوير |
| `npm run build` | فحص الأنواع + بناء نسخة الإنتاج في `dist/` |
| `npm run typecheck` | فحص الأنواع فقط |
| `npm run lint` | فحص جودة الكود |
| `npm run preview` | معاينة نسخة الإنتاج محلياً |

### متغيرات البيئة

```env
VITE_SUPABASE_URL=https://xxxx.supabase.co
VITE_SUPABASE_PUBLISHABLE_KEY=sb_publishable_xxxx
```

**مكان القيمتين في لوحة Supabase:**

- `VITE_SUPABASE_URL` → Project Settings › Data API › Project URL
- `VITE_SUPABASE_PUBLISHABLE_KEY` → Project Settings › API Keys › Publishable key

> ⚠️ **لا تضع** مفتاح `service_role` أو `secret` (`sb_secret_...`) أو كلمة مرور
> قاعدة البيانات في أي ملف داخل المشروع. هذه المفاتيح **تتجاوز الحماية** وتعطي
> صلاحية كاملة على البيانات. المفتاح العام (Publishable / anon) هو الوحيد
> المناسب للواجهة، وهو آمن لأن RLS مفعّل على كل الجداول.

إذا كانت المتغيرات ناقصة، يعرض التطبيق شاشة إعداد عربية توضح ما هو المطلوب
بدل أن ينهار.

## إعداد Supabase

### الخطوة 0 — إذا كانت القاعدة تحتوي جداول قديمة

إذا كان مشروع Supabase مستخدماً قبلاً، قد توجد جداول بنفس الأسماء تتعارض مع
النظام. الأعراض: فشل الـ migration الأول برسالة مثل
`column "role" does not exist` ثم فشل الملفين بعده.

| # | الملف | ماذا يفعل |
|---|---|---|
| 0a | `supabase/sql/00_inspect.sql` | **قراءة فقط** — يعرض ما هو موجود وعدد الصفوف في كل جدول |
| 0b | `supabase/sql/01_reset.sql` | ⚠️ **يحذف** جداول وعروض ودوال Blue Parking فقط |

شغّل `00_inspect.sql` أولاً وراجع النتيجة. إذا كان أي جدول فيه بيانات تحتاجها،
صدّرها من **Table Editor › Export to CSV** قبل الحذف.

`01_reset.sql` **لا يمسّ** الجداول الأخرى ولا حسابات `auth.users` — حساب أبو
حمدان يبقى موجوداً ولا يحتاج إعادة إنشاء.

### الخطوة 1 — تطبيق الـ migrations

**الأسهل — ملف واحد:** الصق كامل [`supabase/sql/INSTALL.sql`](supabase/sql/INSTALL.sql)
في **SQL Editor** واضغط Run. هذا الملف يدمج الـ migrations الثلاثة بالترتيب
الصحيح، فلا مجال لخطأ في الترتيب.

> الملف مُولَّد من مجلد `migrations` — بعد أي تعديل عليها شغّل `npm run db:bundle`.

**أو الملفات منفصلة بهذا الترتيب:**

| # | الملف | ماذا يفعل |
|---|---|---|
| 1 | `supabase/migrations/20260101000000_schema.sql` | الجداول، الفهارس، القيود، التسعيرة الافتراضية |
| 2 | `supabase/migrations/20260101000100_functions.sql` | محرك الحساب، دوال الدخول/الخروج، التقارير، العروض |
| 3 | `supabase/migrations/20260101000200_rls.sql` | سياسات الحماية والصلاحيات |

**أو عبر Supabase CLI** (بلا نسخ ولصق):

```bash
npx supabase login
npx supabase link --project-ref <project-ref>
npm run db:push
```

### الخطوة 2 — إنشاء حساب المالك

من لوحة Supabase: **Authentication › Users › Add user**

- أدخل بريد أبو حمدان وكلمة مرور قوية
- فعّل **Auto Confirm User**

> **أول حساب في المشروع يصبح المالك تلقائياً**، وأي حساب آخر يأخذ صلاحية
> `pending` ولا يرى أي بيانات.
>
> هذا يعمل في الحالتين:
> - **حساب أُنشئ بعد الـ migrations** → trigger على `auth.users` ينشئ الملف الشخصي
> - **حساب أُنشئ قبلها** → الـ migration الأول يتعرّف عليه ويعطي أقدم حساب صلاحية
>   `owner` تلقائياً، ويطبع اسمه في الـ output
>
> إذا كان عندك أكثر من حساب وأردت تحديد المالك يدوياً، شغّل
> `supabase/sql/promote_owner.sql`.

### الخطوة 3 — إيقاف التسجيل العام

**Authentication › Sign In / Providers › Email** → أوقف **Allow new users to sign up**

هذه طبقة إضافية؛ الحماية الأساسية أن أي حساب جديد يأخذ `pending` بلا صلاحيات.

### الخطوة 4 — التحقق

شغّل `supabase/tests/verify.sql` في SQL Editor. هذا ملف قراءة فقط يتحقق من:

- تفعيل RLS على كل الجداول
- وجود حساب مالك واحد
- صحة محرك حساب الرسوم على كل الحالات المعتمدة
- عدم وجود أي دالة متاحة للدور المجهول
- سلامة البيانات (لا دخول مزدوج، لا خروج قبل دخول، لا رسوم على المشتركين)

### (اختياري) بيانات تجريبية

`supabase/seed/dev_seed.sql` يضيف سيارات واشتراكات وعمليات وهمية لتجربة الواجهة
والتقارير. كل صف مُعلّم بـ `[بيانات تجريبية]` وفي نهاية الملف قسم لحذفها.
**لا تشغّله على قاعدة بيانات فيها بيانات حقيقية.**

## النشر على GitHub Pages

### 1) ضبط القيم في GitHub

**Settings › Secrets and variables › Actions › Variables** → أضف:

| الاسم | القيمة |
|---|---|
| `VITE_SUPABASE_URL` | رابط مشروع Supabase |
| `VITE_SUPABASE_PUBLISHABLE_KEY` | المفتاح العام |

(يمكن وضع المفتاح في Secrets بدل Variables — الـ workflow يقرأ من الاثنين.)

### 2) تفعيل Pages

**Settings › Pages › Build and deployment › Source** → اختر **GitHub Actions**

### 3) النشر

كل `push` على `main` يشغّل: `npm ci` → `lint` → `typecheck` → `build` → نشر.
الـ workflow يفشل برسالة واضحة إذا كانت المتغيرات ناقصة.

الرابط: `https://<username>.github.io/blue-parking/`

### ملاحظات مهمة للنشر

- التطبيق يستخدم **HashRouter** (`#/entry`) لأن GitHub Pages لا يدعم
  SPA fallback. لا تغيّره إلى `BrowserRouter` بدون إضافة `404.html`.
- `base` في `vite.config.ts` مضبوط على `/blue-parking/`. إذا غيّرت اسم
  المستودع، غيّر `REPO_BASE` أيضاً.
- الكاميرا تحتاج **HTTPS** — تعمل على GitHub Pages وعلى `localhost`، ولا تعمل
  على `http://` من عنوان IP في الشبكة المحلية.

## قواعد حساب الرسوم

التسعيرة **مخزّنة في قاعدة البيانات** وتُعدّل من شاشة الإعدادات بلا أي تعديل
على الكود.

**القاعدة المعتمدة (معتمدة من أبو حمدان):**

| الإعداد | القيمة |
|---|---|
| فترة الدوام | **08:00 → 15:00** |
| المبلغ الأساسي | **1 د.أ** — يغطي من دخل داخل فترة الدوام |
| الزيادة | **1 د.أ** عن كل ساعة أو جزء من ساعة |
| فترة السماح | **15 دقيقة** بعد الثالثة |
| الدخول قبل 08:00 | **يُحاسب** — 1 د.أ عن كل ساعة أو جزء منها قبل الثامنة |
| أيام الإغلاق | **الجمعة والسبت** — لا يوجد دوام |

### أمثلة محسوبة

| الدخول | الخروج | المبلغ | السبب |
|---|---|---|---|
| 08:00 | 14:00 | **1.00** | داخل الدوام |
| 09:00 | 15:00 | **1.00** | داخل الدوام |
| 09:00 | 15:15 | **1.00** | داخل فترة السماح |
| 09:00 | 15:16 | **2.00** | تجاوز السماح → ساعة كاملة من 15:00 |
| 09:00 | 16:00 | **2.00** | ساعة بعد الثالثة |
| 09:00 | 16:01 | **3.00** | ساعتان (جزء الساعة = ساعة) |
| 09:00 | 20:00 | **6.00** | خمس ساعات بعد الثالثة |
| 16:00 | 17:00 | **2.00** | دخول بعد الدوام → ساعة واحدة من لحظة الدخول |
| 07:00 | 14:00 | **2.00** | ساعة قبل الثامنة |
| 06:00 | 14:00 | **3.00** | ساعتان قبل الثامنة |
| 07:00 | 16:00 | **3.00** | ساعة قبل + ساعة بعد |

### قرارات تصميمية مهمة

**1. المبلغ الأساسي يغطي فقط من دخل داخل فترة الدوام.**
الدخول قبل الثامنة يُحاسب عن كل ساعة أو جزء منها قبل بداية الدوام — تماماً كما
تُحاسب الساعات بعد الثالثة.

**2. الدخول بعد نهاية الدوام يُحاسب من لحظة الدخول.**
سيارة تدخل 16:00 وتخرج 17:00 تُحاسب ساعة واحدة (2 د.أ) لا ساعتين — لا تُحاسب
على وقت لم تكن فيه في الموقف. المبلغ الأساسي يمثّل الحد الأدنى لأي زيارة.

**3. نهاية الدوام تُحسب على تاريخ الدخول، لا تاريخ الخروج.**
الموقف لا يستقبل مبيتاً، لكن هذا يضمن أن أي سيارة تتجاوز منتصف الليل بالخطأ
تُحاسب على كل ساعاتها بدل أن تُفلت بدينار واحد.

**4. الفواتير القديمة محصّنة.**
كل عملية وقوف تحتفظ بـ `pricing_rule_id` الخاص بها، فتعديل التسعيرة يؤثر على
العمليات الجديدة فقط.

**5. المشتركون شهرياً بلا رسوم.**
السيارة ذات اشتراك ساري تُسجّل كـ `monthly`، ويمنع قيدٌ في قاعدة البيانات
احتساب أي مبلغ عليها.

**6. أيام الإغلاق تنبيه لا قيد.**
في يوم الجمعة أو السبت يظهر تنبيه في الرئيسية وفي شاشة الدخول، لكن التسجيل يبقى
ممكناً — حتى لا يتعطّل العمل إذا فتح الموقف استثنائياً.

### كل الإعدادات قابلة للتعديل من شاشة الإعدادات

| الإعداد | القيمة الحالية |
|---|---|
| فترة الدوام | 08:00 → 15:00 |
| المبلغ الأساسي | 1.00 د.أ |
| مبلغ الساعة الإضافية | 1.00 د.أ |
| فترة السماح | 15 دقيقة |
| طريقة التقريب | جزء الساعة = ساعة كاملة |
| احتساب الدخول المبكر | مفعّل |
| أيام الإغلاق | الجمعة، السبت |

## الأمان

### الطبقات

1. **RLS مفعّل على كل الجداول** — الجدول الثمانية كلها، بلا استثناء.
2. **الوصول مشروط بـ `is_owner()`** — دالة `SECURITY DEFINER` تتحقق أن
   `auth.uid()` يملك `role = 'owner'` في `profiles`.
3. **لا وصول للدور المجهول** — كل صلاحيات `anon` مسحوبة على الجداول والدوال.
4. **جداول المال للقراءة فقط من الواجهة** — لا يوجد `INSERT`/`UPDATE` على
   `parking_sessions` أو `payments`. كل كتابة تمر عبر دوال قاعدة بيانات.
5. **المبالغ تُحسب في قاعدة البيانات** — الواجهة ترسل الأمر فقط، ولا تستطيع
   تمرير مبلغ. حتى لو تلاعب أحد بالطلب من المتصفح، المبلغ يُحسب من
   `entry_time` و `exit_time` وقاعدة التسعير.
6. **قيود على مستوى الصفوف** — فهرس فريد جزئي يمنع عمليتين نشطتين لنفس
   السيارة، وقيود `CHECK` تمنع الخروج قبل الدخول والمبالغ السالبة ورسوماً على
   المشتركين وتواريخ اشتراك غير صحيحة.

### ما تم التحقق منه فعلياً

طُبِّقت الـ migrations على **بيئة Supabase محلية كاملة** (نفس صورة قاعدة البيانات
و GoTrue و PostgREST المستخدمة في الإنتاج) واختُبر:

**الأمان**
- حساب ثانٍ مسجّل الدخول: **صفر صفوف** في كل جدول وكل عرض، وكل دالة ترفضه
- الدور المجهول: `permission denied` على كل جدول وكل دالة
- المالك: لا يستطيع تعديل `amount_due` أو إنشاء دفعة مباشرة
- RLS مفعّل على الجداول الثمانية، ولا دالة واحدة متاحة لـ `anon`

**منطق العمل**
- 13 حالة حساب رسوم — كلها مطابقة للمتوقع
- منع الدخول المزدوج، الخروج المزدوج، الخروج بدون دخول
- تعديل التسعيرة لا يغيّر الفواتير القديمة
- اكتشاف أيام الإغلاق (الجمعة والسبت)
- trigger الحساب: الأول `owner` والثاني `pending`

**التطبيق end-to-end** (تسجيل دخول حقيقي عبر GoTrue)
- دخول سيارة بأرقام عربية `١٢-٣٤٥٦٧` ← توحّدت إلى `1234567`
- إنشاء السيارة تلقائياً عند أول دخول
- معاينة المبلغ ثم تسجيل الخروج والدفع
- ظهور العملية في «السيارات الموجودة» ثم في التقارير والإحصائيات

### الدوال المتاحة للواجهة

| الدالة | الوظيفة |
|---|---|
| `lookup_plate(plate)` | بحث عن سيارة + اشتراكها + عمليتها النشطة |
| `register_entry(plate, …)` | دخول — ينشئ السيارة إن لم تكن مسجّلة، ويكشف الاشتراك |
| `preview_exit(session_id)` | معاينة المبلغ قبل التأكيد |
| `register_exit(session_id, …)` | خروج — يحسب المبلغ ويسجّل الدفعة |
| `settle_session(session_id, …)` | تحصيل مبلغ عملية سابقة غير مدفوعة |
| `get_dashboard()` | إحصائيات الرئيسية |
| `get_report(from, to)` | تقرير فترة |
| `calculate_parking_fee(…)` | محرك الحساب |

## قراءة اللوحة (OCR)

- المحرك الحالي **`tesseract.js`** — مجاني ويعمل **بالكامل داخل المتصفح**.
  الصورة لا تُرسل إلى أي خادم خارجي، ولا يوجد أي API مدفوع.
- الصورة تُعالَج قبل القراءة (قصّ الإطار الأوسط، تكبير، تدرّج رمادي، رفع تباين)
  لرفع فرصة القراءة الصحيحة.
- **النتيجة لا تُعتمد تلقائياً أبداً.** الرقم المقروء يُعرض في حقل قابل للتعديل،
  والمشغّل هو من يؤكّد. في الموقف، رقم خاطئ يعني تسجيل خروج سيارة أخرى أو حساب
  مبلغ غلط — فالتأكيد اليدوي ليس تنازلاً عن الجودة بل شرط سلامة.
- إذا فشلت القراءة تظهر رسالة:
  **«تعذر قراءة اللوحة، يرجى إدخال الرقم يدوياً»** والإدخال اليدوي متاح دائماً.
- المحرك **قابل للاستبدال**: نفّذ واجهة `OcrEngine` في
  `src/services/ocr/types.ts` واستدعِ `setOcrEngine()` — بلا أي تعديل على الشاشات.
- كل محاولة تُسجَّل في `ocr_captures` (الرقم المقروء، الرقم المصحّح، درجة الثقة)
  لقياس الدقة وتحسينها لاحقاً.

> محرك القراءة (~2 ميجابايت) يُحمَّل **عند أول استخدام فقط** ثم يُخزَّن في
> المتصفح، فلا يؤثر على سرعة فتح التطبيق.

### توحيد أرقام اللوحات

الرقم الأصلي يُحفظ **كما أدخله المستخدم**، ويُستخدم `plate_normalized` للبحث فقط:

- الأرقام العربية-الهندية (٠-٩) والفارسية (۰-۹) → `0-9`
- صور الألف `أ إ آ ٱ` → `ا` · الألف المقصورة `ى` → `ي`
- حذف المسافات والشرطات والنقاط والتطويل والتشكيل
- الحروف اللاتينية → Uppercase

**ما لا يُوحَّد عمداً:** `ة → ه` و `ؤ/ئ → و/ي`، ولا تُحذف الأصفار البادئة —
حتى لا تتحوّل لوحتان مختلفتان إلى نفس القيمة.

الدالة موجودة في مكانين متطابقين: `public.normalize_plate` في قاعدة البيانات
(المرجع النهائي) و `normalizePlate` في `src/lib/plate.ts` (للبحث الفوري في
الواجهة). **عند تعديل إحداهما عدّل الأخرى.**

## النسخ الاحتياطي

**تصدير CSV** من شاشة التقارير — يفتح مباشرة في Excel بترميز عربي سليم
(BOM + فاصلة منقوطة) وبعناوين أعمدة عربية.

> ⚠️ تصدير CSV يحفظ **سجل العمليات فقط**. لا يحفظ الاشتراكات ولا الإعدادات ولا
> التسعيرة ولا بنية قاعدة البيانات. إذا حدثت مشكلة في مشروع Supabase، الـ CSV
> وحده **لا يعيد النظام**. للنسخة الكاملة استخدم:
>
> - `supabase db dump` من الـ CLI، أو
> - Database › Backups في لوحة Supabase (النسخ التلقائي متاح في الخطط المدفوعة)
>
> كذلك: **الخطة المجانية في Supabase توقف المشاريع غير النشطة** بعد فترة من
> عدم الاستخدام. الاستخدام اليومي للموقف يكفي لإبقائه نشطاً.
